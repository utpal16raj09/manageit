# M3 — Payments (Rent + Token Reservation)

## Scope
- **Recurring rent generation**: Scheduled cron job to automatically generate monthly rent invoices.
- **Razorpay integration**: Processing payments securely via Razorpay's API and Webhooks.
- **Payment history/receipts**: View past transactions and download receipts.
- **Overdue tracking**: Accurately track outstanding balances, including partial payments.
- **Token/reservation payment**: Support for initial deposit/booking payments on the public site.

## Common Agent Bugs
- **Trusting the client-side "payment successful" callback** instead of verifying via the Razorpay webhook. This is a critical security flaw leading to fake success exploits.
- **Recurring rent generation cron timing bugs**, such as double-firing or skipping a month on edge-of-month dates (e.g., Feb 28 vs 31st).
- **Missing idempotency keys** on payment creation, causing a network retry to double-charge a tenant.
- **Flawed overdue calculation** that uses a boolean wall-clock "days since due" without accounting for partial payments, causing a tenant who paid half to still show as fully overdue.

## Definition of Done
- [ ] Payment status is only ever marked "successful" after webhook confirmation, never from frontend response alone.
- [ ] Duplicate payment attempts (e.g. double-click, retry) don't double-charge.
- [ ] Rent generation tested across a month boundary (e.g. 28/30/31-day months).
- [ ] Partial payments correctly reduce the overdue amount, not just flip a boolean.

## Rigorous Testing Plan

### 1. Webhook Security Testing
- **Test:** Manually trigger a "Success" payload from the frontend *without* a Razorpay webhook.
- **Expected Result:** Database status remains `PENDING`.
- **Test:** Use Razorpay webhook simulator to fire `payment.captured`.
- **Expected Result:** Database status transitions to `SUCCESS`.

### 2. Idempotency & Concurrency Testing
- **Test:** Send two identical payment creation requests within 50ms of each other.
- **Expected Result:** Only one Razorpay order is generated; the second request returns the same order ID or is rejected.

### 3. Edge-of-Month Cron Testing
- **Test:** Mock the server date to January 31st, create a lease, then advance the date to February 28th and run the cron.
- **Expected Result:** February rent is generated successfully.
- **Test:** Run the cron twice on the same day.
- **Expected Result:** Rent is only generated once.

### 4. Partial Payment Tracking
- **Test:** Tenant owes ₹14,000. Pay ₹4,000 via Razorpay.
- **Expected Result:** Dashboard shows outstanding dues of ₹10,000 (not ₹14,000, and not ₹0).
